# Worker Studio

Worker Studio is a hackathon MVP that turns a problem statement into an approved specialist team and a controlled, revisable landing page. It implements a real vertical slice across the six source user stories without claiming that simulated capabilities are live.

## What works

- Prompt sufficiency check with one focused clarification question
- Input-dependent problem interpretation and worker recommendations
- Explicit worker selection and approval before generation
- Schema-driven landing page generation with approved-worker gating
- Conversational full-page revisions for copy, theme, feature definitions, and section structure, with destructive-change safeguards
- Persistent project visuals generated by Content Executive with `gpt-image-2.5-flare`
- End-user feature cards that run their assigned approved worker live inside the generated solution
- Separate capability-expansion approval flow
- Live support classification that never claims to create an external ticket
- Refresh-safe projects and project separation
- All eight required product events
- Signed guest ownership, idempotent mutations, and SQL Server 2014 persistence APIs
- Device-only demo fallback when production persistence is disabled

## Local development

```bash
npm install
npm run setup:local
npm run dev:local
```

After a project is built, the **Worker Lab** appears below its generated page. Select all six specialists during approval to demo every capability: voice intent extraction, support classification, content generation, campaign planning, customer-success journeys, and growth analysis. The Landing Page Manager is the seventh worker and orchestrates interpretation, generation, and revisions.

The complete acceptance contract is tracked in [`docs/acceptance-matrix.md`](docs/acceptance-matrix.md). Run `npm run acceptance` for the local type, lint, unit, production-build, and desktop/mobile browser gates. Run `node scripts/verify-production-api.mjs .env.local http://localhost:3000` against a running server for real SQL Server, OpenAI, image persistence, event, worker, and two-project evidence.

`setup:local` prepares the ignored `.env.local` from `E:\Users\env.production`, imports the OpenAI key from `D:\backend\web\config.js`, generates a local guest-session secret, and enables SQL Server persistence. The API key stays server-side. The app also works without an OpenAI key when `NEXT_PUBLIC_DEMO_MODE=true`.

```env
OPENAI_API_KEY=replace_with_openai_api_key
OPENAI_MODEL=gpt-4o-mini
OPENAI_IMAGE_MODEL=gpt-image-2.5-flare
NEXT_PUBLIC_DEMO_MODE=true
```

## Production SQL Server

The intended production database is `ezassist_2_0_0_2_dev`. Set these variables in Vercel and use `NEXT_PUBLIC_DEMO_MODE=false` to switch the interface from local storage to the production API routes:

```env
AZURE_SQL_SERVER=...
AZURE_SQL_PORT=1433
AZURE_SQL_DATABASE=ezassist_2_0_0_2_dev
AZURE_SQL_USER=...
AZURE_SQL_PASSWORD=...
AZURE_SQL_ENCRYPT=true
AZURE_SQL_TRUST_SERVER_CERTIFICATE=false
GUEST_SESSION_SECRET=replace_with_at_least_24_random_characters
NEXT_PUBLIC_DEMO_MODE=false
```

The API never returns credentials or full environment details. Every project query is scoped to a signed HTTP-only guest session. Every mutation requires an `Idempotency-Key` header.

Before deployment, verify connectivity without changing the database:

```bash
npm run readiness -- E:\Users\env.production
```

The persistence adapter uses parameterized `mssql` queries over TDS 7.4 and does not depend on Prisma. The deployment creates only prefixed `WorkerStudio*` tables and can be rerun safely.

```bash
npm run db:deploy -- E:\Users\env.production
npm run db:check -- E:\Users\env.production
```

## OpenAI activation

The API key is intentionally a placeholder. Once supplied, the analysis and page-build routes use the Responses API with Zod-backed structured outputs and a 45-second timeout. Until then, the deterministic engine keeps the full demo path functional.

Only the active problem, interpretation, approved worker definitions, page schema, and requested change are eligible model inputs. Database credentials, guest secrets, and unrelated projects are never sent.

## Current delivery limits

- No account system, public publishing, billing, team permissions, analytics dashboard, or historical restore UI
- Voice and analytics are simulated
- Campaign and customer-success actions are draft-only
- No external ticket, message, or campaign is sent
- Production schema deployment and Vercel configuration require an explicit release step
